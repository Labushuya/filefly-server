FileFly Server — Test Manifest

Manual QA checklist for the self-hosted, invite-based file-receiving server.

Base URL: http://filefly.home (or http://<host>:8000) Auth: Authorization: Bearer <jwt> Version: /version
Pass Fail Open Set the status per block using the dropdown; this is a static QA sheet.
Scope: covers health/version, invite lifecycle, chunked upload, conflict strategies, permission & path-traversal enforcement, guest expiry/max-uses, role restrictions, auth failures, and CORS. Run against a freshly started instance with a known ADMIN_INVITE_CODE. Replace $TOKEN with the JWT returned by the relevant invite.
G01

Health & version endpoints reachable

Steps

  1. Start the server (Docker or uvicorn app.main:app).
  2. Call the two public endpoints — no auth header.
# no token needed
curl -s http://filefly.home/health
curl -s http://filefly.home/version

Expect

/health returns {"status":"ok"} with HTTP 200. /version returns {"version":"0.1.0"} (or the installed version). Swagger UI loads at /docs.
G02

Redeem admin invite → receive JWT

Steps

  1. Use the configured ADMIN_INVITE_CODE.
  2. POST it to the validate endpoint.
curl -s -X POST http://filefly.home/auth/invite/validate \
  -H "Content-Type: application/json" \
  -d '{"code":"<ADMIN_INVITE_CODE>"}'

Expect

HTTP 200 with a JSON body containing access_token, token_type:"bearer", role:"admin", base_path:"", and permissions = ["upload","mkdir","rename","delete","invite"]. An empty or missing code returns HTTP 400.
G03

Create an invite for each of the 4 roles (as admin)

Steps

  1. Set $TOKEN to the admin JWT from G02.
  2. Create one invite per role; note the generated code each time.
for R in admin user service guest; do
  curl -s -X POST http://filefly.home/auth/invite \
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d "{\"role\":\"$R\",\"base_path\":\"$R-space\"}"
  echo
done

Expect

Each call returns HTTP 200 with an Invite object: an 8-char code, the requested role, the given base_path, used_count:0, and the role's default permissions (admin=upload/mkdir/rename/delete/invite, user=upload/mkdir/rename, service=upload, guest=upload). GET /auth/invites then lists all created invites.
G04

Chunked upload — init → chunk → complete (small & large file)

Steps

  1. Redeem a user invite (from G03) to get a user $TOKEN.
  2. Small file: one chunk. Init with chunk_count:1, send chunk index 0, complete.
  3. Large file: split into N chunks (each ≤ MAX_CHUNK_SIZE_MB). Init with chunk_count:N, send all N chunks, complete.
# init
UID=$(curl -s -X POST http://filefly.home/files/upload/init \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"filename":"note.txt","target_path":"","total_size":5,"chunk_count":1,"conflict_strategy":"rename"}' \
  | python -c 'import sys,json;print(json.load(sys.stdin)["upload_id"])')

# chunk 0 (multipart form: upload_id, chunk_index, chunk file)
echo -n "hello" > c0.bin
curl -s -X POST http://filefly.home/files/upload/chunk \
  -H "Authorization: Bearer $TOKEN" \
  -F "upload_id=$UID" -F "chunk_index=0" -F "chunk=@c0.bin"

# complete
curl -s -X POST http://filefly.home/files/upload/complete \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "{\"upload_id\":\"$UID\"}"

Expect

Init returns {"upload_id": "..."}. Each chunk returns {"upload_id","chunk_index","received"} with received counting up. Complete returns {"status":"complete","path":"..."} and the reassembled file exists under STORAGE_ROOT. Completing before all chunks arrive returns HTTP 400 with "Missing chunks: [...]". The staging dir .filefly_tmp/<upload_id> is removed afterward.
G05

Conflict handling — overwrite / rename / skip

Steps

  1. Upload dup.txt once (any strategy) so it exists.
  2. Re-upload dup.txt three times, once with each conflict_strategy: skip, rename, overwrite.
  3. List the directory after each to observe the result.

Expect

skip → complete returns {"status":"skipped","path":...}; original untouched, no new file.
rename → a new file appears with an auto suffix (dup_1.txt, then dup_2.txt, …); original untouched.
overwrite → the existing dup.txt content is replaced; no extra file.
G06

Permission enforcement — user cannot write outside base_path

Steps

  1. Create a user invite with base_path:"userspace" and redeem it.
  2. Attempt an upload/mkdir with a target_path/path that tries to reach a sibling or parent directory (e.g. "../adminspace").

Expect

The resolved path is confined to STORAGE_ROOT/userspace. Any target that resolves outside it is rejected with HTTP 403 "Path traversal not allowed". A normal relative path inside the base works.
G07

Path-traversal protection — ../ is blocked

Steps

  1. With any valid token, call /files/list with a traversing path.
  2. Repeat for upload/init and mkdir targets.
curl -s "http://filefly.home/files/list?path=../../etc" \
  -H "Authorization: Bearer $TOKEN"

Expect

Every request whose resolved path escapes the allowed base returns HTTP 403 "Path traversal not allowed". No file outside STORAGE_ROOT (or the invite base) is ever read, written, or listed.
G08

Guest invite with expiry + max_uses

Steps

  1. As admin, create a guest invite with a near-future expires_at and max_uses:2.
  2. Redeem it twice (each redeem increments used_count).
  3. Redeem a third time.
  4. Separately, create a guest invite that has already expired and try to redeem it.
curl -s -X POST http://filefly.home/auth/invite \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"role":"guest","base_path":"drop","max_uses":2,"expires_at":"2026-12-31T23:59:59Z"}'

Expect

First two redemptions succeed (200 + JWT). The third returns HTTP 403 "Invite exhausted". An expired invite returns HTTP 403 "Invite expired". max_uses:0 means unlimited.
G09

Service account — upload only, no mkdir/rename/delete

Steps

  1. Redeem a service invite (permissions = ["upload"] only).
  2. Upload a file (init/chunk/complete) — should work.
  3. Attempt /files/mkdir, /files/rename, and DELETE /files/delete.

Expect

Upload succeeds. Each of mkdir/rename/delete returns HTTP 403 "Permission 'mkdir'|'rename'|'delete' required". Listing still works (needs only upload).
G10

Directory operations (mkdir / rename / delete) by role

Steps

  1. As user (permissions upload/mkdir/rename): create a dir, rename it, then attempt to delete it.
  2. As admin (all permissions): create, rename, and delete a dir/file.
# user: mkdir
curl -s -X POST http://filefly.home/files/mkdir \
  -H "Authorization: Bearer $USER_TOKEN" -H "Content-Type: application/json" \
  -d '{"path":"","name":"reports"}'

# user: rename
curl -s -X POST http://filefly.home/files/rename \
  -H "Authorization: Bearer $USER_TOKEN" -H "Content-Type: application/json" \
  -d '{"path":"reports","new_name":"reports2"}'

# user: delete  -> should be forbidden
curl -s -X DELETE http://filefly.home/files/delete \
  -H "Authorization: Bearer $USER_TOKEN" -H "Content-Type: application/json" \
  -d '{"path":"reports2"}'

Expect

User: mkdir returns {"created":...}, rename returns {"renamed":...}, delete returns HTTP 403 "Permission 'delete' required". Admin: all three succeed, deleting a directory removes it recursively.
G11

Auth — expired / invalid JWT rejected with 401

Steps

  1. Call a protected endpoint with a garbage token.
  2. Call it with a token signed by a different SECRET_KEY (or an expired one — set JWT_EXPIRE_HOURS very low and wait).
  3. Call it with no Authorization header.
curl -s -o /dev/null -w "%{http_code}\n" \
  http://filefly.home/files/list \
  -H "Authorization: Bearer not-a-real-token"

Expect

Invalid or expired tokens return HTTP 401 "Invalid token" (JWT decode failure covers both bad signature and expiry). A missing bearer header returns HTTP 403 from the security dependency. Changing SECRET_KEY invalidates all previously issued tokens.
G12

LAN-only / CORS behaviour

Steps

  1. With default ALLOWED_ORIGINS=*, send a request with an Origin header and inspect the CORS response headers.
  2. Restart with ALLOWED_ORIGINS=http://filefly.home and repeat with a disallowed origin.
  3. Confirm the server is only reachable on the LAN (not published to the public internet by the reverse proxy).
curl -s -D - -o /dev/null http://filefly.home/health \
  -H "Origin: http://filefly.home"

Expect

With *, the response includes permissive Access-Control-Allow-Origin. With a restricted list, only listed origins are reflected; others are not granted CORS access. There is no public authentication path — access requires an invite code, and the service should only be exposed on the trusted LAN (verify no public port-forward / WAN route reaches it).
